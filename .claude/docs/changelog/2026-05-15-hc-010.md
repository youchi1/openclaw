# 2026-05-15 — HC-010: restore params.buttons reader for the Telegram message tool

## Summary

Customer agent on `patched/2026.5.7-patched.2` called the `message` tool with
`buttons: [[{text, callback_data}], …]`. Telegram delivered the text, but no
inline keyboard rendered. The same call shape worked on `patched/2026.4.12`.
The bootstrap "boss" docs at `/opt/bootstrap/boss/TOOLS.md` still instruct the
agent to *"Use `message` tool (action `send`, `buttons` param) for questions"*,
so every agent currently using that contract on 5.7 was silently shipping
text-only messages where a keyboard was expected.

## Root cause

Between 2026.4.12 and 2026.5.x upstream renamed the message tool's structured
field from `interactive` to `presentation` and rewrote
`resolveTelegramButtonsFromParams` in
`extensions/telegram/src/action-runtime.ts`.

`patched/2026.4.12`:

```ts
function resolveTelegramButtonsFromParams(params) {
  return resolveTelegramInlineButtons({
    buttons: readTelegramButtons(params),
    interactive: params.interactive,
  });
}
```

`patched/2026.5.7`:

```ts
function resolveTelegramButtonsFromParams(
  params,
  presentation = normalizeMessagePresentation(params.presentation),
) {
  return resolveTelegramInlineButtons({
    interactive: presentation ? presentationToInteractiveReply(presentation) : params.interactive,
  });
}
```

Both `readTelegramButtons` and the `buttons:` line were removed. The
downstream `resolveTelegramInlineButtons` in
`extensions/telegram/src/button-types.ts` still accepts a `buttons` arg
(`params.buttons ?? buildTelegramInteractiveButtons(...)`), so half the
plumbing survived — the orphan is direct evidence the removal was
incomplete.

The `message`-tool schema in `src/agents/tools/message-tool.ts` no longer
declares a top-level `buttons` field at all. Typebox passes unknown fields
through, so the agent's `buttons` value lands in the action runtime; the
action runtime just doesn't read it anymore.

Net effect: agents calling the documented contract ship messages without
keyboards. No error, no log line, no callback path. Silent.

## Fix

`extensions/telegram/src/action-runtime.ts`:

- Restored `readTelegramButtons(params)` in its 2026.4.12 form (validates
  each row, requires `text` and `callback_data`, enforces 64-byte callback
  limit via `fitsTelegramCallbackData`, validates `style` against the same
  `["danger", "success", "primary"]` enum).
- Added `coerceTelegramButtonsParam` so a JSON-string `buttons` value
  (`'[[{...}]]'`) is `JSON.parse`-d before the array check. The Anthropic
  tool-input view on the affected VPS showed the value as a JSON string
  in the transcript; supporting both shapes is defensive against whichever
  serialization any given LLM picks.
- Re-imported `normalizeOptionalString` / `normalizeOptionalLowercaseString`
  from `openclaw/plugin-sdk/text-runtime` and `fitsTelegramCallbackData`
  from `./approval-callback-data.js`. Reused the existing
  `TelegramButtonStyle` / `TelegramInlineButtons` types from
  `./button-types.js`.
- Re-wired `resolveTelegramButtonsFromParams` to pass
  `buttons: readTelegramButtons(params)` alongside the existing
  `interactive` / `presentation` paths.

`extensions/telegram/src/action-runtime.hc-buttons.test.ts` — new file, 9
regression tests:

1. Raw `[[{text, callback_data}]]` array shape produces the right
   `sendMessageTelegram` opts.
2. JSON-string `buttons` value (the LLM-serialized form) is parsed and
   produces the same opts.
3. `style: "danger"` is preserved through to the keyboard rows.
4. Malformed JSON string throws `/malformed JSON string/`.
5. Non-array (e.g. `{ rows: [] }`) throws `/must be an array of button rows/`.
6. Missing `text` or `callback_data` throws `/requires text and callback_data/`.
7. `callback_data` longer than 64 bytes throws `/callback_data too long/`.
8. Absent / `null` / `undefined` `buttons` returns `undefined`.
9. `presentation` path still works when `buttons` is absent (regression
   guard against re-breaking the upstream contract this fix preserves).

## Operational impact

After publishing `2026.5.7-patched.4` and rolling out:

- Existing agents calling `message` with `buttons: [[...]]` will once again
  render inline keyboards in Telegram, matching the documented `boss`
  contract.
- The `presentation` path is unchanged; any newer caller using
  `presentation: { blocks: [{ type: "buttons", buttons: [...] }] }`
  continues to work.
- Multi-select / Done accumulator behaviour (HC-007) is unaffected; this
  fix is at the keyboard-build layer, not the callback dispatch layer.

## Why this is upstream-worthy

The half-removed `resolveTelegramInlineButtons` signature (still accepts
`buttons`) shows the 2026.5.x rename was incomplete. Either upstream
should restore the `params.buttons` reader, or finish the removal by
also dropping the orphan param on the downstream resolver and rewriting
the field-tested agent contract. Filing this once `2026.5.7-patched.4`
is rolled out and the customer's Telegram is verified green.
