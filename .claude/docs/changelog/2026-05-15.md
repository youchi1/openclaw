# 2026-05-15 — HC-009: validate runtime auth-profile snapshot mtimes against disk

## Summary

Customer's gateway pre-skipped `anthropic` with a "billing issue" message on every
boss run, even though on-disk `auth-state.json` had no `disabledUntil`. The HeadClaw
controller's `/provider/status` reported `active=false` correctly (banner hidden,
because disk said clean), but every model call still failed without an HTTP request
ever being made. Only a gateway restart recovered.

## Root cause

`resolveRuntimeAuthProfileStore` in `src/agents/auth-profiles/store.ts` returned
the in-memory runtime snapshot of the auth-profile store unconditionally once
populated. There was no mtime validation against disk. Two ways for snapshot and
disk to desync:

1. **Cross-process write.** Anything outside the gateway that calls
   `markAuthProfileUsed` → `saveAuthProfileStore` writes to disk only — that
   writer has no in-process snapshot, so the `hasRuntimeAuthProfileStoreSnapshot`
   guard in `saveAuthProfileStore` returns false and the gateway's main snapshot
   stays frozen at the old `disabledUntil`.
2. **Same-process write to a different agentDir.** `saveAuthProfileStore` only
   refreshes a snapshot for the exact `agentDir` it was called with, and only
   when one already exists for that dir. Agent-scoped writes that affect what
   the merged main store would return leave the main snapshot untouched.

Downstream, `model-fallback.ts` calls `resolveProfilesUnavailableReason(...)`
against `params.authStore` (the snapshot). When that returns `"billing"`, it
returns a `skip` decision before any HTTP call. No HTTP call means no fresh
`markAuthProfileFailure`, which means no fresh disk write, which means the
disk state never updates from a real provider response. Locked in until the
gateway restarts.

## Fix

`src/agents/auth-profiles/runtime-snapshots.ts`:
- Added a parallel `runtimeAuthStoreSnapshotMtimes` map keyed the same way as
  the snapshot map.
- `setRuntimeAuthProfileStoreSnapshot` and `replaceRuntimeAuthProfileStoreSnapshots`
  capture current mtimes (`auth-profiles.json` + `auth-state.json`) at the time
  the snapshot is recorded.
- `clearRuntimeAuthProfileStoreSnapshots` clears the mtimes map alongside the
  snapshot map.
- New exports: `getRuntimeAuthProfileStoreSnapshotMtimes`, type
  `AuthProfileSnapshotMtimes`.

`src/agents/auth-profiles/store.ts`:
- New private helper `refreshRuntimeAuthProfileStoreSnapshotIfStale(agentDir)`.
  Compares recorded mtimes against current disk mtimes; if they diverge,
  reloads from disk via `loadAuthProfileStoreForAgent(agentDir, { readOnly: true })`
  and calls `setRuntimeAuthProfileStoreSnapshot` to refresh.
- `resolveRuntimeAuthProfileStore` calls the helper for both the main store and
  (when the agent path differs) the requested agentDir, before reading either
  snapshot.

`src/agents/auth-profiles.runtime-snapshot-refresh.test.ts` (new):
- TDD-written regression test. Seeds a snapshot with `disabledUntil`, simulates
  a cross-process write that clears the cooldown on disk (bumping mtime), then
  asserts the next read returns the cleared state.
- Second test confirms a stable-mtime read returns the snapshot unchanged.

## Why this is upstream-worthy

This is a generic cross-process consistency bug. Any deployment where a probe,
cron, controller, or other CLI/script touches the auth store while a long-lived
gateway is running can hit it. HeadClaw surfaces it acutely because the
controller checks disk state and the gateway checks snapshot state — but the
underlying contract violation exists everywhere.

## Operational impact

After publishing `2026.5.7-patched.3` and rolling out:
- New billing failures still produce real `disabledUntil` markers as before.
- The gateway snapshot now follows disk on the next read, so any out-of-band
  clear (probe, retry, controller, manual edit) takes effect within one read
  instead of requiring a restart.
