# 2026-05-19 — HC-006 amend: also fix `finalAssistantText` path

## Summary

Customer reported the duplicate-Telegram-delivery symptom HC-006 was supposed to
fix had re-appeared on cu — onboarding prompt "What roles fit you best? Tap all
that apply, then Done ✅" delivered twice (once with buttons, once without).
Diagnosis showed the original HC-006 port was incomplete: it only patched the
block reply path, leaving a parallel reply-payload path that produces the same
duplicate through a different code branch.

## Root cause

The original HC-006 (commit `9881929629`) split `text` (fallback-replaced) from
`blockReplyText` (raw NO_REPLY) and routed only the block reply path through the
new `blockReplyText`. The PATCHES.md description claimed both paths were fixed,
but the actual diff missed this line in
`src/agents/pi-embedded-subscribe.handlers.messages.ts`:

```ts
const finalAssistantText = silentExpectedWithoutSentinel ? "" : text;
```

`finalAssistantText` feeds `assistantTexts` →
`buildEmbeddedRunPayloads` (`src/agents/pi-embedded-runner/run/payloads.ts`) →
final reply payload. The silent-token filter at `payloads.ts:477` only catches
literal "NO_REPLY". Because the fallback replaces NO_REPLY with the tool's
content before reaching that line, the filter saw real text and let the payload
through. Result: the same duplicate, by a different route.

The original HC-006 test only asserted on `emitBlockReply.mock.calls`, so the
gap in the `finalAssistantText` path stayed hidden.

## Fix

One-line change: route `finalAssistantText` through `blockReplyText` instead of
`text`. New TDD regression test (`HC-006 amend: finalizeAssistantTexts receives
raw NO_REPLY (not fallback tool text)`) reproduces the exact cu screenshot and
verifies `finalizeAssistantTexts` is invoked with raw `NO_REPLY` rather than
fallback content. Test fails red on the original HC-006 code with the tool text
leaking into the payload pipeline; passes green after the amend.

## Why the original miss happened

Two layers shipped silently broken: (1) the patch description in PATCHES.md
documented an intent (`finalAssistantText` path covered) that was not in the
diff, and (2) the regression test only asserted on `emitBlockReply.mock.calls`,
which would have flagged the block-reply path but not the payload-builder
path. The test was tied to one symptom site, not the contract.

This is the third HC patch (after HC-001 partial fix, HC-008 part 2 subsumption
miss) where "what PATCHES.md says" and "what the diff does" diverged enough to
matter. Worth treating as a process signal: when a patch description claims
multiple fix locations, the test should assert on each location, not just one.
