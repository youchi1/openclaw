# 2026-04-07/08 — Skills & Bootstrap Hot-Reload Fix (HC-001, HC-002, HC-003, HC-004)

## Summary

Fixed four-layer bug preventing user-installed skills and bootstrap file changes from appearing in agent sessions.
Skills installed to `~/.openclaw/skills/` were invisible to running agents despite
`openclaw skills list` showing them as "ready". Root cause spanned snapshot caching,
filesystem watching, and OpenAI prompt caching.

## The Problem

HeadClaw customers install skills on VPS machines. After installing a skill, agents in
existing sessions never see it. The agent's `<available_skills>` system prompt block
stays frozen with whatever skills were present when the session was first created.

Upstream issues: openclaw/openclaw#54209, openclaw/openclaw#44898
Upstream PRs reviewed but not cherry-pickable: #55007, #54228 (code diverged in v2026.4.5)

## Debugging Process — Layer by Layer

### Layer 1: Snapshot never rebuilt (HC-001)

**Symptom:** `openclaw skills list` shows the skill, but agent sessions don't.

**Investigation approach:**

1. Read `src/agents/skills/workspace.ts` — skill loading and merging logic. Looked correct.
2. Read `src/auto-reply/reply/session-updates.ts` — snapshot refresh logic. Uses
   `shouldRefreshSnapshotForVersion()` which returns `false` when both cached and current
   versions are 0.
3. Searched for all callers of `ensureSkillsWatcher()` — found it was ONLY called from
   `session-updates.ts`, never from `agent-command.ts`.

**Root causes found:**

- `agent-command.ts` (used by CLI agent, cron, plugin SDK) never started the filesystem watcher.
  Without the watcher, the snapshot version stayed at 0 forever.
- Both `agent-command.ts` and `session-updates.ts` had a version-0 cold-start bug: when skills
  were installed while OpenClaw wasn't running, watcher never fired, version stayed 0, and
  `shouldRefreshSnapshotForVersion(0, 0)` returned `false`.

**Fix:** Added `ensureSkillsWatcher()` to `agent-command.ts`. Added version-0 bump logic
to both code paths (bump version before the refresh check when both versions are 0).

**Key lesson:** The two code paths (`session-updates.ts` for auto-reply, `agent-command.ts`
for CLI/cron) had diverged — one had the watcher, the other didn't. Always check ALL code
paths that consume a shared resource.

### Layer 2: Chokidar v5 glob patterns broken (HC-002)

**Symptom:** After Layer 1 fix, watcher was started but still no events fired when
skills were added/removed.

**Investigation approach:**

1. Wrote a self-contained Node.js script to test chokidar directly:
   ```js
   chokidar.watch("~/.openclaw/skills/*/SKILL.md", { ignoreInitial: true });
   ```
   Created a skill, waited — **zero events fired**.
2. Changed to directory watching:
   ```js
   chokidar.watch("~/.openclaw/skills", { ignoreInitial: true, depth: 1 });
   ```
   Created a skill — **add/change/unlink all fired correctly**.

**Root cause:** Chokidar v5 resolves glob patterns at startup. New subdirectories created
after the watcher starts don't match the already-resolved glob. This is a behavior change
from chokidar v3/v4.

**Fix:** Changed `resolveWatchTargets()` to return skill root directories instead of glob
patterns. Watcher uses `depth: 1` and filters for `SKILL.md` in event handlers.

**Key lesson:** When testing filesystem watchers, always test with a self-contained script
that creates AND deletes files — don't assume the watcher works because the code looks right.
Chokidar's glob behavior is version-dependent and not well-documented for edge cases.

**Testing note:** Vitest worker threads don't play well with chokidar's FS watchers —
e2e watcher tests must use `node --import=tsx` directly, not vitest.

### Layer 3: OpenAI prompt cache serving stale system prompt (HC-003)

**Symptom:** After Layer 1+2 fixes, the snapshot was correctly rebuilt (verified via
`sessions.json` — 19 skills including the new one, prompt contains it). But the LLM still
said "No, not in the current `<available_skills>` block I have for this session."

**Investigation approach:**

1. Added `OPENCLAW_DUMP_PAYLOAD=1` debug instrumentation to `attempt.ts` — dumps system
   prompt, messages, and post-turn cache usage to `/tmp/openclaw-dump/`.
2. Pre-turn dump confirmed: `systemPromptHasStealth: true` — skill IS in the prompt.
3. Post-turn dump revealed: `cacheRead: 21888, input: 192, total: 22174` — **98.7% cache hit**.
   OpenAI was serving almost the entire request from cache, including the OLD system prompt.

**Root cause:** `buildOpenAIResponsesParams()` set `prompt_cache_key: options?.sessionId`.
OpenAI's Responses API docs say the key is "combined with the prefix hash", implying
automatic invalidation. In practice, with GPT-5.4 and long conversations (70+ messages),
OpenAI served the stale cached prefix despite the system prompt changing.

**Fix:** Include a SHA-256 hash of `context.systemPrompt` in the cache key:

```ts
prompt_cache_key: `${sessionId}:${sha256(systemPrompt).slice(0, 12)}`;
```

When the system prompt changes, the hash changes, forcing a cache miss. Normal turns
(same prompt) get the same hash and cache hits work normally.

**Verification:**

- Fresh session after fix: `cacheRead: 7680` (partial hit — cache priming), Stealth Browser listed
- Second turn same session: `cacheRead: 15360` (full cache hit, system prompt stable)
- The fix covers ALL system prompt changes: skills, soul.md, HEARTBEAT.md, bootstrap files, etc.

**Key lesson:** Never trust that a provider's caching "just works" for dynamic system prompts.
Always verify with actual cache hit/miss metrics. The `OPENCLAW_DUMP_PAYLOAD=1` instrumentation
was essential — without seeing the raw `cacheRead` numbers, we would have continued debugging
the wrong layer.

**Provider-specific notes:**

- **OpenAI Responses API:** Uses `prompt_cache_key` for routing. Key must change when prompt
  changes. Prefix hash combination may not work reliably for long conversations. Our hash fix
  is a reliable workaround.
- **OpenAI Chat Completions API:** Uses automatic prefix matching only (no explicit cache key).
  No fix needed — prefix changes automatically invalidate.
- **Anthropic:** Uses `cache_control` breakpoints with stable/dynamic split via
  `OPENCLAW_CACHE_BOUNDARY`. Not affected by this issue — the boundary marker explicitly
  separates cacheable and non-cacheable portions.
- **Google:** Uses separate prompt caching mechanism (`google-prompt-cache.ts`). Not investigated
  in this session — may have similar issues if it uses session-pinned cache keys.

## Debug Instrumentation (kept in codebase)

Set `OPENCLAW_DUMP_PAYLOAD=1` to dump pre-turn and post-turn data to `/tmp/openclaw-dump/`:

- `{ts}-system-prompt.txt` — full system prompt text
- `{ts}-messages.json` — conversation history summary (roles, content lengths, previews)
- `{ts}-meta.json` — session ID, provider, model, skills presence checks
- `{ts}-cache-usage.json` — input/output/cacheRead/cacheWrite token counts

This was invaluable for diagnosing the Layer 3 cache issue and should be preserved for
future provider-level debugging.

## Reproduction Checklist (for similar issues on other providers)

1. **Verify skill loading:** `openclaw skills list` — does the skill show as "ready"?
2. **Verify snapshot:** Check `~/.openclaw/agents/<id>/sessions/sessions.json` — does
   `skillsSnapshot.skills` include the skill? Does `skillsSnapshot.prompt` contain it?
3. **Verify system prompt:** Set `OPENCLAW_DUMP_PAYLOAD=1`, run an agent turn, check
   `/tmp/openclaw-dump/*-system-prompt.txt` — is the skill in `<available_skills>`?
4. **Verify cache behavior:** Check `/tmp/openclaw-dump/*-cache-usage.json` — what's the
   `cacheRead` ratio? If >90% and the system prompt changed, the provider is serving stale cache.
5. **Verify LLM sees it:** Ask the agent to list skills. If system prompt has it but LLM doesn't
   list it, it's either cache (check step 4) or attention/context-length degradation (try fresh session).

### Layer 4: Bootstrap files cached in-memory with no invalidation (HC-004)

**Symptom:** After fixing skills (HC-001-003), bootstrap files like `USER.md` and `SOUL.md`
still required a gateway restart to pick up changes.

**Root cause:** `bootstrap-cache.ts` cached workspace files in a `Map<string, WorkspaceBootstrapFile[]>`
per session key with no staleness check. Once loaded on first turn, never re-read from disk.

**Fix:** Store file mtimes alongside cached entries via `fs.statSync`. Before returning cached
files, compare current mtimes. If any changed or a previously-missing file appeared, reload.
Combined with HC-003 (system prompt hash in cache key), this ensures both file changes and
OpenAI cache invalidation work end-to-end.

**Key lesson:** Always check for ALL caching layers. We found four: skill snapshot cache,
chokidar watcher, OpenAI prompt cache, and bootstrap in-memory cache. Each layer was
independently correct in isolation but broken in combination.
