# 2026-05-15 — HC-007 amend: keep multi-select keyboard visible after Done

## Summary

After deploying `2026.5.7-patched.3` (HC-010) the customer noticed that
multi-select Telegram button messages lost their entire keyboard the
moment they tapped "Done ✅". On `patched/2026.4.12` the keyboard stayed
visible in chat history with the ✅ marks intact. The regression was in
the 5.7 port of HC-007, not in HC-010.

## Root cause

`extensions/telegram/src/bot-handlers.runtime.ts` in the 5.7 HC-007
commit (`bba83ddb2c`) opened the Done-click handler with:

```ts
// Done click: drain selections and dispatch as one message
const selections = drainSelections(chatId, callbackMessage.message_id);
if (selections && selections.length > 0) {
  try {
    await clearCallbackButtons();
  } catch {
    // Best-effort button cleanup
  }
  const mergedText = buildMultiselectResultMessage(selections);
  ...
}
```

`clearCallbackButtons` issues `editMessageReplyMarkup` with
`inline_keyboard: []`, wiping the entire keyboard from the chat. The
4.12 HC-007 commit (`d6acf3eda9`) did NOT have this block. The synthetic
dispatch was the only side effect of Done.

The block almost certainly came in during cherry-pick conflict
resolution when rebasing HC-007 onto 5.7. The surrounding 5.7
callback-handler code (e.g. the `pluginBindingApproval` branch a few
lines below) legitimately clears its keyboard on resolution, and the
pattern got mirrored into the multi-select path where it does not
belong.

`git show bba83ddb2c -- extensions/telegram/src/bot-handlers.runtime.ts`
confirms the lines were part of the HC-007 commit itself, not a later
HC-008/9/10 change. So this is a defect in HC-007 as it lives on 5.7,
not a separate concern.

## Fix

Amended `bba83ddb2c` in place (force-push to `origin/patched/2026.5.7`
followed). The new HC-007 commit hash is `f384a45cc9`. HC-008, the
test(HC) commit, HC-009, and HC-010 were cherry-picked forward onto
the amended HC-007:

| Patch | Old hash | New hash |
|---|---|---|
| HC-007 | `bba83ddb2c` | `f384a45cc9` |
| HC-008 | `2b22d3b868` | `f17c36313e` |
| test(HC) | `d4ae6b4b28` | `a834d94c61` |
| HC-009 | `246dedeccd` | `79e5c61889` |
| HC-010 | `5321c522c5` | `76a8d12e9d` |

The diff against `bba83ddb2c` is a five-line deletion in
`extensions/telegram/src/bot-handlers.runtime.ts` plus a three-line
comment locking in the contract:

```diff
-          // Done click: drain selections and dispatch as one message
+          // Done click: drain selections and dispatch as one message.
+          // Do not clear the keyboard. The ✅-annotated rows stay in chat
+          // history, matching the 4.12 HC-007 contract.
           const selections = drainSelections(chatId, callbackMessage.message_id);
           if (selections && selections.length > 0) {
-            try {
-              await clearCallbackButtons();
-            } catch {
-              // Best-effort button cleanup
-            }
             const mergedText = buildMultiselectResultMessage(selections);
```

## Why amend instead of stacking an HC-011

The five-line block is an obvious port-time defect inside HC-007's own
patch surface, not a separate concern. Keeping HC-007 as one commit
with the correct intent is cleaner for the next upstream upgrade than
stacking a follow-up that would always have to be cherry-picked
alongside HC-007. The trade-off is a one-time force-push on
`patched/2026.5.7` and a hash-shift for every later patch on the
branch. PATCHES.md was updated with the new hashes for HC-007 through
HC-010 in the same bookkeeping commit.

## Verification

- Manual reproduction on VPS `88.198.128.47` against
  `2026.5.7-patched.4`: send a Telegram message with multi-select
  buttons ending in "Done ✅", tap two options, tap Done. Synthetic
  message dispatched; keyboard still visible in the chat with the two
  selected rows showing the ✅ prefix.
- Full Telegram extension suite still green
  (`test/vitest/vitest.extension-telegram.config.ts`).
- `git show f384a45cc9 -- extensions/telegram/src/bot-handlers.runtime.ts`
  no longer contains `clearCallbackButtons` inside the Done dispatch
  block; only `pluginBindingApproval`, plugin-callback-resolution, and
  approval-shutdown paths retain it (those are correct).

## Operational impact

- `2026.5.7-patched.4` is the artifact that carries the fix together
  with HC-010 from earlier today.
- VPS `88.198.128.47` hot-patched and verified before publishing.
- HeadClaw rollout via `OPENCLAW_VERSION=2026.5.7-patched.4` distributes
  the combined fix to every tenant.

## Lessons for the next upgrade

When porting HC-007 to a future release, diff
`extensions/telegram/src/bot-handlers.runtime.ts` against the previous
patched-branch's HC-007 file directly, not against the upstream
release. Conflict resolution that pattern-matches against surrounding
upstream callback handlers can re-introduce a `clearCallbackButtons`
call. The in-source comment block at the start of the Done dispatch
should make the intent obvious during conflict resolution.
